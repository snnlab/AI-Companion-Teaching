# Hosting the classroom roster (Vercel)

This page is for instructors who want every student in a course to submit their project state to one place, so it can be reviewed from a single dashboard instead of opening each student's board one at a time. `/papertrail:host --init` puts a private, per-student-token-gated server on Vercel, the same hosting service `/papertrail:board --publish-web` already uses for the single-project board — but this is a **separate project with a different trust model**: one Vercel project for the whole course, an instructor password that opens the dashboard, and a personal bearer token for each student that `/papertrail:submit` uses instead of a browser. Setting it up takes about 20 minutes once. After that, registering a new student takes one command, and a student's whole experience is: run `/papertrail:submit`, review what it's about to send, and confirm.

The sections below cover, in order: the message to send each student, how to install what you need, what this costs, what to do if something goes wrong, moving to a new computer, what a student actually experiences, and — read this one carefully — what data this involves, because it is a materially bigger privacy surface than the single-collaborator board.

## The message to send each student

There is no single shared password here — every student gets their own personal token, generated by `/papertrail:host --add-student` or `--roster`. Send the server URL to the whole class (a syllabus line or an announcement is fine, since the URL alone grants nothing), then send each student **their own token individually and separately from that announcement** — never in a mass email, never posted where the whole class can see it. Something like:

```
Subject: Submitting your project to the course roster

Hi [name],

To submit your PaperTrail project for review, run this in your Claude Code
session in your project folder:

  /papertrail:submit

The first time, it will ask for two things:
  Server: [URL]
  Token:  [their personal token]

Keep this token to yourself — it identifies your submissions to me
specifically. If you think someone else has seen it, tell me and I'll issue
you a new one.

Before it sends anything, it will show you exactly what's about to go —
review that each time. It includes your full decision log and every signed
plan version, not just your current draft.

Thanks.

[Your name]
```

## Step 0: install Node.js

Same as the single-project board: this tool only needs Python day to day, but hosting anything on Vercel needs Node.js too, for the Vercel CLI.

- Easiest path: go to nodejs.org, download the installer marked "LTS," and run it, accepting the defaults.
- On a Mac with Homebrew, `brew install node` works instead.

Close and reopen your terminal (or restart Claude Code) afterward so it picks up the new program. Then tell Claude Code to run `/papertrail:host --init`. It walks you through the rest, pausing at the points only you can do: logging into Vercel in your own terminal, connecting a private Blob store in the Vercel dashboard, and enabling firewall rate limiting before the first deploy.

Before the first deploy, enable firewall rate limiting for the `/api/login` route in the project's Vercel Firewall settings, exactly as the single-project board requires. This is the primary defense against repeated password guesses against your instructor login, and `--init` will not let you skip it.

## Time and cost

First setup takes about 20 minutes, mostly installing Node and logging into Vercel once. After that, registering a student, rotating a token, or redeploying after a change is one command and a few seconds.

Hosting itself is free on Vercel's "Hobby" plan for personal, noncommercial use — the same plan the single-project board uses. Two things worth checking:

- If your course or institution has any commercial arrangement attached, confirm whether the free plan's noncommercial terms actually apply, or whether you need a paid plan.
- **Check with your institution or IRB before your first deploy, not after.** This server aggregates decision logs and git history from every registered student in one place — see **Data and privacy** below before you send a single token.

## If something goes wrong

**"Node not found."** Follow Step 0, then reopen your terminal.

**A permission error mentioning `npm i -g` or `EACCES`.** Claude runs the Vercel CLI through `npx`, which doesn't need a global install, so you're unlikely to see this. If you do, reinstalling Node from nodejs.org is simpler than repairing the permissions yourself.

**The `vercel login` link expired, or logged into the wrong account.** Run `vercel login` again; if it opened the wrong account, log out first or use a private browser window.

**A student's token was rejected (`401 invalid_token`).** Either it was mistyped, or it was rotated (by you, deliberately, or because you suspected it leaked). Run `/papertrail:host --rotate-token <studentId>` and send them the new one, the same careful way as the first.

**`--add-student`/`--roster` says a student is already registered.** Re-running registration for an existing student **rotates their token** — it does not create a duplicate or fail quietly. If that's not what you meant to do, note that their old token now needs replacing, and send them the new one.

**A submission from a student never shows up on the roster.** Ask them to re-run `/papertrail:submit` and read what it reports — a `401` means their token needs rotating (above), a `413` means their project is over the size limit and needs trimming, and a network error usually means the server URL is wrong or the deployment was removed.

## New computer, or a second instructor account?

There is no dedicated reconnect flow yet for this template (unlike the single-project board's `--web-connect`, which recovers a saved config from the Vercel project's own environment). To pick this project back up on a different machine: re-run the **Materialize the deploy directory** and **Create or link the project** steps from `/papertrail:host --init` — `npx vercel link` inside the freshly copied `plans-admin/.classroom-web/` reattaches to the *existing* Vercel project (by name), rather than creating a second one, as long as you select the right project when the CLI asks. Do not repeat the whole `--init` flow including a **new** Blob store or new secrets; that would orphan the original data. If in doubt, check the Vercel dashboard first to confirm which project already exists before creating anything.

## What a student experiences

1. They run `/papertrail:submit`. The first time, it asks for the server URL and their personal token, which they enter once; after that it's saved locally and every later `/papertrail:submit` just works.
2. Before it sends anything, it shows them exactly what's included — how many components, plan versions, and results bundles, the git commit range, and the total size — and asks for explicit confirmation. It never sends silently.
3. After sending, it tells them what happened in plain language: recorded, or unchanged since last time, or a specific problem (rejected token, oversized submission, malformed data) with what to do about it. It also relays the server's own mechanical re-verification lines, so if something doesn't match what they expect (a checksum mismatch, a signing-date question), they see it immediately rather than only you seeing it later.

They never get a login page or a password for this server — their only credential is the personal token, used solely by the submission command, never a browser session.

## Leaving comments, and how a student finds out about them

Clicking into a student's row on the roster dashboard opens their board exactly as they'd see it themselves, with commenting turned on — select text, leave a comment, the same flow as a `--publish-web` collaborator link. Your comment is attributed to `COURSE_INSTRUCTOR_NAME` if you set it during `--init` (recommended — otherwise the author field starts blank, which silently disables the **Save comment** button until you type a name). A row marked **new** was submitted since your last visit to the dashboard, so you don't have to remember what you've already looked at.

**Sending the feedback.** When you have finished commenting on a student, press **"학생에게 피드백 보내기"** (Send feedback to the student) in the floating panel at the bottom-left of their board. Until you press it, the student sees nothing — your comments sit on the server, in progress. Pressing it marks that submission's feedback as released; pressing it again later (after adding more comments) re-sends and re-lights the student's "새 피드백" badge.

**Where the student reads it.** Each student has a personal page at `<your-server-url>/me`. They open it in any browser, paste the same token they use for `/papertrail:submit` (once — it's remembered), and see the feedback you have released, with a "새 피드백" badge for anything new since their last visit. **They install nothing** for this — no Node, no Vercel, no plugin; the page is a plain static page that reads their own comments with their own token.

**Push notifications (optional).** If you set `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` during `--init` (generate the pair with `npx web-push generate-vapid-keys` inside `plans-admin/.classroom-web/`), the `/me` page shows a "🔔 새 피드백 알림 받기" button. A student clicks it once, allows notifications in the browser prompt, and from then on pressing **"학생에게 피드백 보내기"** delivers a real system notification to their laptop or phone — even with the page closed. No third-party account: a VAPID keypair is just a self-signed identity the browser's own push service accepts. Caveats: the student must click "allow" once (desktop Chrome/Edge/Firefox and Android Chrome are reliable; iOS Safari only if they add `/me` to the home screen first), and a notification failure never blocks the release — the `/me` page is always the fallback. The button's result line reports how many devices were reached.

**Without VAPID keys it is not a push.** The `/me` page then just has to be opened. Either way it is independent of **`/papertrail:check`**, which still works exactly as before: a student can run it any time to pull *every* comment on any of their past submissions into their local session (painted in place on the passage each one targets), whether or not you have pressed "보내기". If you need a student to see something urgently, tell them directly, the same as for any other feedback.

## Data and privacy

Read this section before your first deploy — it involves meaningfully more than the single-collaborator board.

The single-project board, shared with `--publish-web`, exposes **one student's** plans, results, and comments to **one instructor** (or whoever else gets that link). This roster server is different in kind, not just degree: it collects **every registered student's** decision log, every signed plan version, and a git-history excerpt (commit hashes, author dates, author names, and one-line subjects for files under `plans/` — never diffs or full commit bodies) into **one Vercel account you control**. That is a much larger aggregation of individually identifiable student work and behavior in one place, and it deserves the same scrutiny a class roster or gradebook would get, not just the scrutiny one shared document gets.

Before you deploy:

- **Check with your institution or IRB.** If your course, a grant, or an IRB protocol governs how student work and identifying information may be stored, ask *before* the first deploy — not after tokens have already been sent out. This applies with more force here than to the single-project board, because one compromised instructor account now exposes the whole class's submitted history, not one student's.
- **The Blob store's region is fixed at creation**, exactly as for the single-project board — choose it deliberately if data residency rules apply (e.g. GDPR, a funder's data-management plan), and don't accept a default without checking.
- **What Vercel processes:** every registered student's submitted payload (decision log, signed plan versions, results-bundle manifests and artifacts), the git-history excerpt attached to each submission, your own instructor login sessions, and basic access logs (IP addresses, rough geography, timing) for anyone who reaches the server.
- **What the server does NOT do:** it never verifies who a student actually is beyond possession of their token (the same limitation the single-project board's sign-off trailer has — a name in a trailer, or a token in a request, is not a cryptographic identity check). It never grades, sign-off-approves, or blocks a submission for content reasons — every mechanical re-check is advisory, shown to you, never a gate on the student.
- **Deleting a student's data.** There is no dedicated delete-one-student command yet. To remove a student entirely, delete their `roster/<studentId>.json`, `roster-token-index/<their token hash>.json`, and every `submissions/<studentId>/*` blob from the Vercel dashboard's Blob browser, or ask Claude to do it directly against the Blob store. This is not currently a one-command operation — treat it as a manual, deliberate step.
- **Taking the whole server down.** Remove the Vercel project from your account (`vercel remove`, or delete it from the dashboard). This deletes the roster, every student's submitted history, and the Blob store together, irreversibly.
