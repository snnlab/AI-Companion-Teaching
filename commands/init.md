Initialize (or update) the aict workflow in this project. Skill context: read `${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/SKILL.md` first if you have not already.

Follow these steps in order:

1. **Resolve the project root.** If inside a git repository, the root is `git rev-parse --show-toplevel`. If that differs from the current directory, or if this is not a git repository, confirm the intended project root with the student before creating anything. Never nest a second `plans/` tree inside a project that already has one at its root.

2. **Check for prior initialization.**
   - If `plans/master-plan.md` already exists: switch to **update mode**. Never clobber it. Offer to (a) review and refresh the components table together, (b) upgrade a pre-v0.3 master plan in place — add the `### Research questions` subsection, the `Serves` column, and an `Initialized:` line backdated to the git first-commit of master-plan.md — (c) upgrade the CLAUDE.md section (step 6) if the plugin has changed, and (d) add the per-stage model profile via `/aict:models` if `plans/model-profile.md` is missing, and (e) add a `Detail level: standard` line to the master plan if it lacks one (the board's default reader detail; the student can change it to `compact` or `full`), (f) ensure the root `.gitignore` carries the `logs/` line — an accepted offer performs the step-5 append operation immediately, before this mode's "skip steps 3–5" takes effect (rule 9's evidence discipline reaches existing projects only with it), and (g) if the project itself is changing direction, hand off to `/aict:renew`, which archives the master plan and writes a fresh one over the existing work. Skip steps 3–5.
   - If the repo's `CLAUDE.md` contains `<!-- aict:start -->` but `plans/` is missing, tell the student the project looks partially initialized and ask how to proceed.

   **Mid-session adoption.** This command works at session start or mid-session, after exploratory work has already happened. Fold what the session established into the plan artifacts: explored data quirks, sharpened questions, and choices already made become Project context, the research questions, and later Scope-decision reasons — **the session's history feeds the plan, not the log**. The decision log starts at initialization: no entries for pre-init work, no reconstructed timestamps (the same rule as never fabricating entries). Pre-adoption *history* — decisions that predate initialization — is recorded separately and honestly in `plans/history.md` via `/aict:adopt`, never backdated into the log.

   **Adopting substantial prior work.** When the repo already holds months of executed analysis (many scripts and outputs, a long git history) that no plan ever governed, do not reconstruct it here — init derives components from the research design and sets status only. Instead run init in **minimal mode** (project context + research questions + markers + the `Initialized:` stamp; leave the components table with a one-line "components adopted via /adopt" note), then hand off to `/aict:adopt`. That command decomposes the done work into components, drafts a full **retrospective** plan for each (reviewed in one board batch), and reconstructs pre-adoption history into `plans/history.md` — the machinery that lets already-done work carry a real plan without pretending it was prospective.

3. **First, the paper type — a separate, single-question round before anything else.** Ask (AskUserQuestion, one question, two options): **"Is this paper a quantitative analysis, or a literature review?"** — *Quantitative*: the student collects or works with data and fits a statistical model. *Review*: the student systematically searches, screens, extracts from, and synthesizes existing literature (PRISMA-style or similar). Store the answer as `paperType: quantitative` or `paperType: review` — it decides which CLAUDE.md conventions block step 6 installs and how step 4/5 phrase the example components. This is a real fork, not cosmetic: everything downstream (the plan-review-sign-execute loop, the results-bundle schema, the rubric) already works identically for both, so this question exists only to pick the right prose, not to unlock different mechanics.

   **Then the short interview.** If AskUserQuestion is unavailable and `$ARGUMENTS` does not already supply every required answer, create nothing. Print this complete non-interactive recovery form and ask the student to rerun it with real values: `/aict:init Paper type: <quantitative|review>; Paper: <working title>; RQs: <RQ1; RQ2; ...>; Data: source=<source>, rough size=<size>, sensitivity=<classification>; Course: <course name/section, and the paper's due date, or "not given yet">; model profile=<recommended or custom choices>; reader detail=<compact, standard, or full>`. Do not create any file until the rerun supplies those values. Otherwise, ask the student (use AskUserQuestion; keep it to one round, four questions max): **the paper itself** — a working title and, in a sentence or two, what it is about — then **the research questions** (they become the master plan's numbered list: RQ1, RQ2, …), then **the data** (for `quantitative`: sources, rough size, sensitivity; for `review`: the databases/sources the search will draw on, a rough expected corpus size, and any sensitivity — most review searches are `none`, published literature), and the **course and deadline context** (course name/section, and the paper's due date, or "not given yet") — it fills rule 7 of the CLAUDE.md block (output conventions, deadline awareness); "not given yet" leaves generic coursework defaults. `$ARGUMENTS`, if provided, seeds the paper's working title and description — confirm rather than re-ask.

4. **Derive components from the research design, not the repo.** Components are the research activities required to answer the research questions — propose each with a `Serves` entry (`RQ1`, `RQ1, RQ2`, or `—` for genuine infrastructure). For `paperType: quantitative`, components are the usual analysis steps (e.g. `data-prep`, a model fit, a robustness check). For `paperType: review`, components are the review's own methodological stages — typically some or all of `search-strategy` (databases, search terms, date range), `screening` (title/abstract, then full-text, with inclusion/exclusion criteria and a disagreement-resolution rule), `extraction` (the data pulled from each included study into a table), `quality-appraisal` (a risk-of-bias or quality tool, if the review uses one), and `synthesis` (narrative synthesis and/or the PRISMA flow diagram) — propose only the stages this review actually needs, not the full list by default. Then scan the repo (`git log --oneline | tail -30`, top-level directories, existing scripts and data folders) to set **STATUS ONLY** — work that already happened gets `done` or `in progress`, not `not started`. The repo scan never shapes the component structure; never create components that narrate repository history. Keep components at the granularity of "independently completable and verifiable" (see `${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/references/split-criteria.md`). Confirm the list with the student. If demo-style artifacts exist (`plan-versions/`, `askuserquestion-log.md`), mention them and treat them as read-only context; do not migrate or modify them.

5. **Create the artifacts** from the templates in `${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/templates/`:
   - `plans/master-plan.md` from `master-plan.md` — keep the `<!-- aict:master-plan -->` marker on line 1, fill in project context (2–3 paragraphs from the interview), the `### Research questions` list, the confirmed components table with its `Serves` column, today's date (`date +%Y-%m-%d`), stamp `Initialized:` with the real current time (`date +"%Y-%m-%d %H:%M"`), set the `Detail level:` line to the reader-detail answer from the model-profile step below (default `standard`), and add a `Paper type: <quantitative|review>` line from step 3's answer right below it — this is what step 6 reads to pick the matching CLAUDE.md conventions block, including on a later re-run of this command. The template's `Component` column header renders as **`Analysis step`** for `quantitative` and **`Review step`** for `review` (free text — no code parses this string; it exists only so the table reads naturally to the student). Delete the Sequencing notes section unless dependencies are non-linear.
   - `plans/decision-log.md` from `decision-log.md` — header and rules only. **Never fabricate entries for work that predates initialization.** The log starts now.
   - `plans/model-profile.md` — which Claude model each stage runs on. **Before writing it, ask up front (AskUserQuestion): (a) use the recommended per-stage model defaults, or choose your own models? and (b) the reader detail level the board opens plans at — `compact` (the contract: context, goal, decisions, boundaries), `standard` (+ approach, steps, verification), or `full` (+ the agent-detail code blocks); default `standard`.** Write answer (b) into the master plan's `Detail level:` line (above); it sets only the board's default collapse — every plan is authored in full and the reader can always toggle. For (a): on *defaults*, copy the template `model-profile.md` verbatim (the defaults are the recommended profile). On *choose your own*, copy the template, then walk the six stages exactly as `/aict:models` step 2 does — model (inherit / opus / sonnet / haiku / fable / a full `claude-*` id) and effort per stage — and apply the answers to the table, keeping the header prose and the read-only mechanism column intact. Either way write the file **once**, then run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/scripts/models.py generate` a **single** time and relay its output: it writes the three `aict-*` review agents into `.claude/agents/` (committed, ownership-marked), refuses any same-named agent the student owns, and prints a note when `.claude/agents/` was just created — in that case tell the student a restart may be needed before the agents are picked up. The board's Models tab edits this later.
   - `plans/execution/.gitkeep` — write it as an empty file with the Write tool (not `touch`), so the directory survives a git commit. Execution plans are created later by `/aict:plan`.
   - Root `.gitignore` — ensure it contains a `logs/` line (create the file if missing, append the line if absent; never rewrite existing content). Rule 9's evidence logs must never be committable.
   - The mechanical board launcher — run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/scripts/board.py --install-launcher` once to write `./aict-board`, the no-LLM way to open the board (useful when the Claude session is rate-limited: `./aict-board` in a terminal, or `!./aict-board` in the session). It is machine-specific and gitignored via `.git/info/exclude`, so it never enters a commit. Relay the one-line notice it prints. (Every `/aict:board` open re-ensures it, so existing projects pick it up on their next board open.)

6. **Bind the conventions in CLAUDE.md.** Read `${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/templates/claude-md-section.md` for `paperType: quantitative`, or `${CLAUDE_PLUGIN_ROOT}/skills/managing-aict/templates/claude-md-section-review.md` for `paperType: review`. The two files are identical in every rule except 7 (output conventions) and 9 (evidence-before-claims phrasing) — rules 1–6, 8, 10, 11 govern the workflow itself and do not depend on the paper's methodology.
   - If the project has no `CLAUDE.md`, create one containing that block.
   - If `CLAUDE.md` exists without a `<!-- aict:start -->` marker, append the block to the end. Touch nothing else in the file.
   - If a start marker already exists, replace everything between `<!-- aict:start -->` and its matching `<!-- aict:end -->` (inclusive) with the current block. Never duplicate the section; never modify content outside the markers.
   - The block's rule 7 carries a course/deadline placeholder — substitute the interview's answer ("not given yet" when none). When refreshing an existing block, read the current course/deadline value first and preserve it; re-ask only if it is absent.
   - **Refreshing an existing project (update mode, step 2c):** read `Paper type:` from the existing `plans/master-plan.md` and re-apply the matching template — never ask the paper-type question again for a project that already has one, and never mix rule 7/9 from one variant with the rest of the block from the other.
   - **Malformed markers:** if the file has a start marker without its end marker, an end marker without a start, markers in reverse order, or more than one marker pair, stop and show the student what was found — never guess a replacement range over unrelated CLAUDE.md content.

7. **Wrap up.** Verify on disk that every artifact from steps 5–6 actually exists, and report only what exists — if a write was denied or skipped, say so plainly. Then suggest (do not run without approval) a commit such as `plans: initialize aict workflow`. **Point to the right next command:** if the repo scan in step 4 turned up substantial prior work that no plan governed — many analysis scripts/outputs and a long history (roughly 20+ commits) predating this init — recommend `/aict:renew` when the student wants a NEW direction over that work (fresh master plan, archived old one, carried accomplishments) or `/aict:adopt` to reconstruct what happened under the current direction; otherwise point the student at `/aict:plan` to scope the first component.
