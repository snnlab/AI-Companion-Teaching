## AICT workflow

This project uses the AICT workflow (a plan-based bridge between a student and their instructor for a quantitative-methods final paper). These rules apply to every session in this repository:

1. At session start read `plans/master-plan.md`, then the latest `vN.md` for the component you are touching (`plans/execution/<NN-slug>/`).
2. Execution plans `v1.md, v2.md, …` are **never overwritten or edited**. A revision is a new file with a `Supersedes:` line saying what changed and why.
3. Append to `plans/decision-log.md` **as decisions happen** — a clarifying question, a scope change, a non-trivial interpretive call, a surprising result. Never backfill at the end of a session.
4. Surface interpretive choices (variable selection, case exclusions, coding rules, model specification) to the student **before** acting. Do not decide research questions, analytical choices, or interpretation on their behalf.
5. After execution work update the Components table in `plans/master-plan.md` — one line of outcome per component, `Serves` kept current.
6. If work is about to exceed what the current plan covers, pause and say so. Propose a new version rather than drifting.
7. Output conventions — coursework deliverable, not a journal manuscript. Course/deadline context: <course name and section, and the paper's due date, or "not given yet">.
   - Citations: APA style by default, or ASA style if the course/instructor specifies it — ask if unclear, and stay consistent within the paper.
   - Figures and tables: sized and captioned so they can be pasted directly into the paper body (a PNG or an in-document table is fine — this is not a submission to a journal, so skip vector-PDF/LaTeX typesetting unless the student's instructor specifically asks for it). Every figure and table carries a title and a one-line caption a reader could understand without the plan.
   - Keep the paper's deadline in view: when a plan step or a revision would plainly blow past the due date, say so before starting it, rather than silently running long.
8. An execution plan is short, plain-language, and read cold by a coauthor. It is judged on five things: a goal with checkable success criteria; the consequential decisions with real reasons; steps concrete enough that "did the agent do this?" has an answer; a validation step that tests the criteria, not just that code ran; and boundaries. Push code into collapsible `<details class="agent-detail">` blocks.
9. Evidence before claims. Run substantive analysis with output captured to `logs/` (e.g. `2>&1 | tee logs/<date>_<step>.log`; `logs/` stays gitignored). Never report a result — in chat, a results bundle, or a report — without the log, notebook output, or artifact that shows the code actually ran. Logs are local, temporary evidence: never write row-level personal data, credentials, or secrets into them.
10. State working assumptions before acting on them; when an instruction has multiple readings, present them rather than picking silently. Keep changes minimal and surgical.
11. **Never write the paper's sociological interpretation on the student's behalf.** Drafting directions, playing devil's advocate, and critiquing an existing draft are all fine — but the argument, the theoretical implications, and the final interpretive sentences of the paper must be authored by the student in their own words, not generated by the AI as the finished product. If you do draft interpretive prose as a starting point for the student to react to, immediately log a `plans/decision-log.md` entry flagging it — something like "AI drafted interpretive text, student has not yet revised it in their own words" — so the gap between an AI-drafted starting point and the student's actual authored interpretation is never silently absorbed into the final paper.

The `managing-aict` skill (from the aict plugin) has these conventions in depth. The primary loop is plan → draft review → execute gate → tail. If work happened outside that loop or mid-session logging was missed, `/aict:sync` is the recovery checkpoint.
